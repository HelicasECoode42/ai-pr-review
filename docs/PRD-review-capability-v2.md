# AI PR Review 审查能力与模块解耦 PRD

日期：2026-10-14。状态：待用户评审。本 PRD 先于下一轮功能开发；已有分支原型不等于本 PRD 已交付。

用户已支持图分组与恢复方向；实际阶段、测试和边界见 [开发与验收手册](review-v2-development.md)。本文剩余细节仍为设计要求，不代表已实现。

## 1. 产品目标

帮助开发者发现变更中的真实问题，并提供能核对、能行动的解释。提升问题发现能力，同时减少误报与核验误删；能够识别接口契约错乱、实现不完整、过度防御、浅封装和高耦合造成的具体维护成本。

技术栈继续使用 Python + TypeScript。借鉴 Java 后端的职责边界、依赖注入和调用链切片思想，不迁移 Java，不引入仅为分层而存在的转发类、微服务或消息队列。

## 2. 现状与新增能力的区别

| 能力 | 已有事实 | 本次目标 |
| --- | --- | --- |
| GitHub、CLI、Web、VS Code | 已有入口；现有功能需要保持 | 共用应用编排与配置，入口只做适配 |
| 规则与 LLM 隔离 | 主模型不注入规则结论已存在 | 保持独立；规则线索不能成为默认高风险结论 |
| Evidence Gate | 已有新增行原文引用与失败场景检查 | 支持同一固定版本的多文件、base/head 证据；引用真实不能冒充 Bug 已证明 |
| 固定版本读取 | 分支已增加固定 SHA 与读取审计 | 明确覆盖范围、来源及遗漏；不是从零新增“代码引用”能力 |
| 沿变更读取代码 | 分支原型有定义窗口、文本引用搜索 | 形成可解释的变更切片，覆盖入口校验、调用方、契约及副作用 |
| 行为核验 | 分支原型有因果字段、反证与待核实 | 判定入口可达性；允许不同问题类型采用不同证据标准 |
| Critic | 历史试验误删过成立问题 | 保留原候选，统计误删；不能通过少报制造精度提升 |
| 评测 | 历史工程试验约 4% grounded recall；最新一个案例无有效提升结论 | 固定协议的新旧对照，分开报告 Bug 与结构质量；不得宣称未测效果 |

## 3. 用户需要看到的结果

报告分三类：已核实问题、结构与可维护性建议、待核实线索。每项展示问题、涉及代码、成立依据、影响及最小修复方向。待核实项展示缺失的关键证据，不制造“全部安全”的暗示，不自动发为确定的 GitHub 行内问题。

运行失败、证据不足和没有发现是三种不同状态。预算耗尽或检索不完整要明确显示。用户能查看核验前后候选与删除原因。

## 4. 问题判定契约

### 4.1 Bug 和回归

说明实际或合理可达的触发输入、入口至故障点的路径、预期与实际行为，以及变更如何引入或加重问题。依据可来自类型与接口契约、调用方、配置、测试、语言语义及原始实现；不要求每项都有线上事故或已执行测试。

入口检查必须真实存在于所检索版本，不能臆造攻击者、非法状态或未来调用方。不要求证明所有路径；只需一个与支持环境和接口相符的有效路径。公共接口契约内的边界值可以直接构成触发条件，不应因未找到仓库内调用者就否定公共 API 回归。

核验状态为 confirmed、dismissed、needs_context。只有明确反证才能 dismissed；信息缺失进入 needs_context。格式问题允许有界重试，不直接抹掉原候选。不得单独依据模型自信度、意见票数或严重度删除问题。

### 4.2 结构与可维护性问题

不强制套用运行时 Bug 的“故障路径”模板。需指出可见结构事实、涉及的职责或依赖、具体维护代价及可落地改善，例如三个入口复制模型配置而产生行为漂移，或业务服务同时负责网络读取、判断与发布导致难以独立测试。

浅封装本身不是问题：如果提供稳定契约、隔离外部 SDK、控制预算或改善替换测试，它有价值。无契约、无策略且引入多层转发、字段漂移和重复修改的封装，可以列为结构建议。

高耦合需要依赖事实或共同修改的具体例子，不能仅以文件长、参数多、类数量少判定。结构建议单独评测，不灌入 Bug Recall；若使用 ReviewBench 广义发现指标，明确其包含 maintainability/testing/documentation 等类别。

### 4.3 过度防御代码

应审查吞异常返回空结果、重复且矛盾的校验、契约保证后仍散布无价值空值分支、无边界重试、无意义兜底及默默改变参数。检查防御所在信任边界、上游保证和失败语义。

- 外部输入、网络响应、数据库历史数据及第三方结果需要合理校验；不能机械建议删除。
- 内部已验证对象的重复防御若增加分支而没有新增保障，列结构建议并说明契约依据。
- 吞掉错误、伪装成功、重试放大副作用等造成可观察错误，列 Bug/可靠性问题。
- 推荐最小局部修复：在正确边界集中校验、显式失败或有记录的降级；禁止为了修一个问题增加层层 try/catch、重复适配器和无依据回退。

## 5. 避免审查器自身过度防御

证据要求与问题类型相符，而不是无限加门槛。新增行是评论锚点，不能要求所有证据也在新增行；调用方和被删代码可支撑变更回归。不能要求结构建议先造成运行崩溃。

允许代码语义支持的判断，不把“未执行测试”自动等同于不成立。引用、入口和因果核验分别记录，避免格式失误变成语义否定。保留未通过候选供审计；核验预算耗尽属于不完整，不属于无问题。

验收同时测核验保留率、成立候选误删数、待核实中的成立问题比例，以及 final Recall。候选发现不足与核验损失分别诊断；只提升 Precision 而明显损失 Recall 不能接受为默认策略。

## 6. 变更切片与多视角发现

从变更符号及其契约构建切片：旧定义与新定义、输入解析/前置校验、调用方、返回值消费者、异常与副作用、相关测试及配置。索引与摘要只用于检索，判定回到原始代码。

Python 优先可靠 AST；其他语言通过可替换索引适配器渐进增强。文本命中必须标注为引用候选，不能宣称解析到真实调用图。跨服务、动态分派或检索限制必须显示覆盖不足。

可配置发现视角：逻辑与边界、接口与契约、安全与权限、状态与资源、架构与可维护性。视角是审查任务，不要求每个都是独立 Agent 或一次独立模型调用。先测共享切片的多视角提示，再测分开调用的增益与成本；统一候选去重和核验。

规则为独立信号，不默认引导主发现。需要旁路验证的信号也遵循对应判定契约。

## 7. 低耦合工程边界

| 模块 | 责任与产物 | 禁止承担 |
| --- | --- | --- |
| SnapshotReader | 固定版本代码与来源 | 模型判断、发布 |
| ChangeSlicer | 变更定义、关系、覆盖与遗漏 | 最终 Bug 判断 |
| EvidenceRetriever | 按请求返回原始证据 | 评分与风险决策 |
| CandidateDiscoverer | 按视角产生有类型候选 | 直接发布、删除其他视角候选 |
| BehaviorVerifier | 因果、反证和缺失信息 | 改评分标签、修改目标代码 |
| DecisionPolicy | 各类型判定与预算决策 | 隐式网络/模型请求 |
| Reporter/Publisher | 报告与授权发布 | 重新判断问题真假 |
| ApplicationRunner | 编排、取消、阶段状态与恢复 | 复制各模块实现 |

使用有类型阶段输入输出，替代共享 dict 的隐含键。Snapshot、Provider、Budget 显式注入；配置读取和网络客户端创建集中于应用入口。只在真实替换点定义接口，禁止一方法一服务的浅封装。

每阶段可独立复跑和测试；阶段检查点包含 repo/base/head、审查器版本、策略哈希、模型及阶段。报告格式版本化兼容，保留已有 GitHub Actions、Web、VS Code 行为。

## 8. 模型与预算

允许 Python 直接调用 DeepSeek Flash。模型选择、思考强度、上下文、输出上限、重试和总体预算分别配置。记录请求模型和实际返回模型，不以别名承诺模型权重固定。

充值记录与当前 Key 的余额查询不能互相替代。预算由用户指定，不从余额变化推断意图；不展示密钥，不自动更换账户。费用结算可能延迟，余额显示不变不能认定调用免费。

## 9. 分阶段执行与验收

1. PRD 评审完成后，先做应用入口与有类型边界的渐进解耦。保持行为兼容，独立分支、Draft PR，不合并 main。
2. 补入口可达性检索，建立真实回归样例：null 被入口拒绝、公有 API 合法边界、吞异常误判成功、重复防御只有维护成本、多文件返回值契约改变。
3. 固定模型与预算做同案例新旧对照；保存全部候选与判定。报告 Precision、Recall、类别、核验误删、失败、时延与用量；一个案例不能宣称整体改善。
4. 分别消融切片、多视角与核验；有成本和召回证据后再决定默认开启策略。已研究案例属于开发集；另选未参与优化的留出样本，标签不进入发现/优化输入。
5. 最后才考虑配置自优化；不允许修改评测标签、评分和固定测试集。

发布验收：现有接口兼容；失败不伪装成功；原候选可追溯；关键回归用例通过。质量验收：同协议对照报告完成；新增门槛不能误删已成立回归样例；拟改为默认的策略须提高 Recall 且不超出预先约定的 Precision/成本容忍范围。具体数值目标在可信基线后确定，不编造当前可达指标。

## 10. 本轮非目标

不迁移 Java、不重写全部产品、不以 Agent 数量衡量能力、不自动执行任意目标仓库命令、不自动合并 PR、不把“引用真实”包装成新增可靠性成果，不把未评测的原型宣称为能力提升。

## 11. 任务分发、恢复与回滚（补充需求）

低耦合必须覆盖运行时：提交请求与耗时审查分离，阶段失败隔离，任务状态持久化，工作进程可替换。当前 Web SSE 使用进程内 Queue + Thread，不是持久化任务队列，服务崩溃后不能依赖它恢复。

建议部署形态为 Python API + 独立 Celery Worker + Redis 调度/限流缓存 + PostgreSQL 任务与阶段记录。Redis 不是唯一恢复真源；Redis 与 RabbitMQ 均能作为 Celery broker，首次实施先按运维环境确认。CLI 和 GitHub Action 保留直接执行模式，共用同一阶段协议；不能强迫所有用户部署队列。Temporal 可作为未来复杂持久化工作流方案，不与 Celery 同时叠加。

提交时在数据库事务中写 ReviewRun 和 Outbox；分发器将 run_id 投递队列。Worker 领取带期限的阶段租约，凭 attempt/fencing token 更新结果，拒绝失效 Worker 写回。数据库记录输入哈希、状态、尝试次数、预算、产物位置与错误；队列只传引用，不传整个源码或密钥。产物与阶段成功记录提交后才确认消息。周期扫描未分发 Outbox 与过期租约，实现 Redis 故障或 Worker 崩溃后的恢复。

任务去重键含 repo/base/head、策略版本、模型配置；主动重跑有显式新 run_id。恢复仅复用相同输入和策略的已完成阶段，不能混用不同 commit。并行发现视角只读共享切片，各自产生独立批次，汇总达到完成/截止条件后进入核验；失败视角标记不完整，不能阻塞其他已完成产物或伪装全覆盖。

429、暂时网络/服务故障有次数与总时间上限的退避；401/402/配置错误进入暂停或人工处理，不循环消费。重试耗尽记录失败任务与原因，支持人工重新投递。按模型、用户、仓库限制并发，核验与发现使用明确预算，GitHub 发布单独隔离。取消不允许后续阶段发布结果。

不承诺 exactly-once 模型调用：远端成功但本地未保存就崩溃，可能再次付费。保存请求状态与已返回产物，未知结果进入显式 reconcile 状态，结合提供商能力和用户预算决定是否重发；不能称为可撤销费用。至少一次投递要求所有持久化与外部副作用幂等。

### 回滚语义

- 执行恢复：从最后成功阶段继续；不删除旧审计记录，也不回滚已经发生的模型费用。
- 策略回滚：保存不可变策略版本和上一稳定版本，评测不达标时切回稳定版本；在途任务继续固定旧版本或显式取消，禁止中途换配置。
- 产物回滚：新版报告作为新版本生成，原有效报告保留，成功后才切换 current 指针。
- 外部副作用补偿：GitHub 发布前确认当前 PR head；利用 publication intent、稳定标识和远端查询避免重试重复发评论。已发布错误报告可更正或标记被替代，删除行为遵循已有授权；这属于补偿而非数据库事务回滚。
- 代码部署回滚：保留上一构建；数据库 schema 与事件格式采用先兼容扩展、后清理，保证旧 Worker 与 API 可恢复运行。

### 故障验收

杀死 Worker 后，其他 Worker 可恢复未完成阶段且不重复提交已完成结果；Redis 重启后能从数据库重建待处理任务；消息重复投递不重复发布；旧租约持有者无法覆盖新结果；PR head 变化不发布旧报告；402 停止无效重试；新策略失败可切回稳定版本；SSE 断开不终止任务，重连可读取数据库状态及带序号的阶段事件。

上述能力目前是 PRD 要求，尚未实现。先以故障验收定义接口，再决定具体队列配置和部署规模，不能只安装 Redis 就声称获得恢复能力。

参考：Celery tasks https://docs.celeryq.dev/en/stable/userguide/tasks.html；Temporal Python https://docs.temporal.io/develop/python。

## 12. 同类实现、规模与速度质量约束

2026-10-14 文档研究：阿里 OpenCodeReview 用相关文件分组、受控工具检索、独立定位和复核，提供会话恢复。其效率与精度指标属于项目方在自身实验条件下的报告，同时明确召回取舍；不能直接移植为本项目收益。PR-Agent 可参考 Python 集成和上下文预算，Claude Code Review 插件可参考独立视角和复核。公开实现与商业服务不等价，必须标注比较范围。

来源： https://github.com/alibaba/open-code-review ，https://github.com/The-PR-Agent/pr-agent ，https://github.com/anthropics/claude-code/blob/main/plugins/code-review/commands/code-review.md 。

本地工具 Python 源码约 57 文件、9,298 行；目录体积受依赖、缓存与报告影响，不代表业务规模。不因代码行数直接引入微服务。工具自身阶段复杂度与被审目标仓库规模分别衡量。

大仓库执行策略：首次按固定 commit 建立定义/引用索引；后续按内容 hash 增量更新。对所有变更记录覆盖状态，按依赖关系组成有大小上限的 ReviewUnit，跨单元依赖通过证据引用连接；大单元继续拆分，不截取前若干文件冒充全覆盖。各单元有界并发、共享只读缓存，避免每个视角重复载入整个仓库。复杂、低覆盖或有待核实候选的单元进入定向深查，简单变更也不能无条件跳过。

提供快速与深入两种策略，均展示范围和遗漏。默认先完成基础发现，再按需核验/检索；策略是否降低召回通过消融确认。按 provider 限流、队列深度和剩余预算调度；并发只降低墙钟耗时，不能声称降低 tokens。MQ 改善分发和恢复，也不会让一次模型推理天然更快。

实验指标包括最终 Precision/Recall、核验误删、每 PR 和每 ReviewUnit 时延、首个结果耗时、P50/P95、排队与模型耗时分解、tokens、重试成本、缓存命中、变更覆盖、失败恢复时长。预算不足明确 partial。目标延迟和成本上限先测代表性小/中/大 PR 后确定，不能以删候选或裁剪变更达标。

成熟度还包含：稳定且版本化的接口和产物；部署与 schema 迁移回退；可观测事件和请求追踪；仓库/用户权限隔离、凭证与日志脱敏；取消、超时与背压；用户确认/拒绝问题及拒绝原因；可复现回归集；新版本灰度比较。反馈是后续标注线索，不能把用户接受/未接受直接等同于真/假，也不能直接修改独立测试标签。

## 13. Benchmark 选择与使用边界

现有 ReviewBench 继续作为开发与回归评测，不删除历史负结果。另从 AACR-Bench 选择尚未研究的 Python/TS 与跨文件案例作为外部留出候选；检查与现有样本重合，固定版本、语言/规模/类别分层抽样，正式评测前不把标注用于调提示词。AACR 提供仓库级案例和统一评测框架，接口适配与 judge 协议必须逐项核对。

Martian code-review-benchmark 提供离线标注评测与在线开发者后续修复分析，可补充观察真实使用价值；在线采用修复作为信号不能等同于全部真实 Bug，未被修复也未必是误报。不同 benchmark 的类别、分母与 judge 不同，不混合成一个无说明 Recall。

推荐证据组合：外部固定留出样本衡量泛化；内部行为回归集检验已知误报/漏报/过度防御；实际 PR 灰度数据衡量时延、成本和可用性。功能测试数不替代审查质量。小批量作为开发诊断，不代表统计稳定的排名；不以项目热度或供应商自报榜单决定架构。

## 14. Python 分组与 token/cache 设计依据

已从用户提供书籍的 nav/ncx 目录定位并阅读《深入理解 AI Agent：设计原理与工程实践》2.3、2.3.3、2.3.4、2.7.4、2.7.7。重点采用稳定前缀、工具大输出外置与上下文隔离；书中供应商价格和具体 Harness 内部实现属于说明材料，不作为当前 API 定价/行为保证，需以供应商文档与实测核对。

公开参考：Aider 的 aider/repomap.py 提取定义/引用，建立 NetworkX 图并 PageRank 排序，在预算内生成 repo map。它是上下文选择实现，不是现成的审查分组器，更不是完整语义调用图。OpenCodeReview 的关联文件组提供分组设计参考；本项目的 ReviewUnit 划分算法是拟设计方案，尚未从其代码移植。Deep Agents 的 filesystem/summarization middleware 提供大工具结果外置、历史归档与压缩参考；pi 的 compaction 文档提供保留近期历史、结构化摘要参考。不因此整体迁移这些框架。

### 无模型的分组步骤

1. Git diff hunk 映射到变更符号；Python ast 提取定义、import、Call 等节点，多语言通过 Tree-sitter 适配。语法引用可有歧义，关系边记录 kind、解析来源和确定程度，不能伪装成运行时调用证明。
2. 固定 base/head 建立符号表与引用关系。节点为变更符号，强边来自可解析依赖/契约，弱边来自目录、同名符号和测试映射。公共高连接节点作为共享证据，不把整仓库黏成一个组。
3. 强关联优先合并；预计上下文超预算就沿弱边拆开。大型连通分量必须继续有界划分，不能只用 connected_components 后得到超大组。所有 diff hunk 至少归属一个单元；跨单元关系记录可补读的链接。
4. 每单元包含必须的变更和定义，额外上下文按相关性排预算；候选核验优先补输入校验与消费者。分组稳定排序，记录成员、边界及遗漏。token 估算有误差，需要记录模型实际 usage。
5. 以 Pydantic ReviewUnit 保存 unit_id、snapshot、symbols、hunks、evidence_refs、token_budget、coverage；数据库保存后队列仅分发 run_id/unit_id。LLM 接收单元内容，缺证据返回只读请求，由 Python 执行。

### 三种缓存不能混称

- 源码/索引缓存：应用可控制，键至少含租户/仓库、blob hash、解析器版本；减读取与索引成本，不自动减少模型输入 tokens。
- 阶段结果缓存：同输入、策略、模型配置的已完成产物可复用，真正避免一次模型调用；新策略或相关依赖改变必须失效。缓存结果不等于再次模型执行。
- 模型 KV / API prefix cache：托管 DeepSeek 的内部 KV 由供应商控制，Python 不能把它放进本地 Redis。应用通过稳定消息前缀提高跨请求命中机会；输入仍计为逻辑 tokens，但缓存命中可能按不同价格计费。缓存非保证命中，不能把摘要 ID 当成模型已读原文。

提示顺序建议：稳定阶段指令和工具 schema → 稳定目标项目指导/单元原始证据 → 本轮请求、候选与新增读取。动态时间/run_id 不放前缀；源码顺序与 JSON 序列化固定。发现和核验职责不同，可各自保持稳定模板，不能为缓存强迫共用不合适的指令。预算允许时维持追加式证据；必须裁剪/换阶段时接受部分缓存重建，不为了命中持续携带无关代码。

检索先返回有界 path/line/预览，read 再提供定义窗口或所需原始行；大输出归档，冻结展示预览。最终核验不能只凭摘要。历史摘要仅用于长会话，需要计算额外总结调用成本和一次性前缀重建成本；短审查优先不引入总结模型。

小批量 d9e9b16 的新流程第三次请求：prompt_tokens=13,508，cache_hit=13,312，cache_miss=196，completion=4,555，含 reasoning=2,689。它表明当前 API 已有命中，不证明总费用免费或有固定节省比例；前三次仍有共 23,983 输出 tokens，输入缓存不能消除这部分费用。低思考强度也不等于关闭思考。

验收拆开报告：输入总量、缓存命中/未命中、输出/思考、调用次数、缓存复用次数、成本、时延与 Recall。先测上下文选择/重复消除，再测前缀布局与缓存；不以缓存命中率单项作为优化目标。
