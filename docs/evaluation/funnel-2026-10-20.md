# 审查漏斗：N → S → D → P（2026-10-20）

本文回答两个问题：**现在这条审查链路到底怎么流**，以及**每一层丢了多少**。所有数字都有复现命令，S 完全离线免费；D/P 需要一次已保存的运行产物（位置 proxy，不是语义裁决）。

## 一、真实链路（不是"全量扫描 + AI 问一次"）

```
PR metadata + diff
  │
  ├─ 1. 确定性扫描（规则 / AST / Ruff）           ← 只产出 signal，不作为结论
  │     src/analyzer/risk_rules.py, deterministic_tools.py
  │
  ├─ 2. 选材 S: build_review_context              ← 这就是 S 层
  │     - patch token 预算（默认 12000；超预算按 triage→文件优先级→大小→路径排序）
  │     - 文档 / lockfile / 敏感路径排除，逐 hunk 记 complete/partial/omitted
  │     - 默认不启用 unit 切片（实测 9/146 units、558k tokens，比截断更差）
  │     src/analyzer/context_builder.py
  │
  ├─ 3. 自动证据补充 S: EvidenceBundle.follow     ← 也是 S 层（免费）
  │     从 changed 定义出发读源码窗口，按 head/非测试/定义优先级/成本 seed，
  │     再按 symbol search 找调用方
  │     src/analyzer/repository_context.py
  │
  ├─ 4. Discovery D: review_grounded 第一段        ← 这就是 D 层
  │     一次调用返回 intent_hypotheses + 有界 context_requests + candidates
  │     host 只执行"绑定到 hypothesis id 的 read/search"（每轮≤4，总请求有预算）
  │     可多轮 discovery（默认 3；unit 路径 1）
  │     src/reviewer/grounded_review.py
  │
  ├─ 5. Verification P: review_grounded 第二段
  │     confirmed / dismissed / needs_context + counter_evidence + 引文
  │     （可选 missing-evidence 第二次 verify slot，默认关闭）
  │
  ├─ 6. 判据与过滤 P: criteria v4 + filters
  │     chain 完整性、source provenance（引文必须来自实际发送的文本）、
  │     witness 机械求值、契约域检查、confidence/去重/每文件上限
  │     src/reviewer/criteria.py
  │
  └─ 7. 发布 P
        suggestions = confirmed 且通过过滤；pending = needs_context/unverified
        进报告但不发 inline comment；decision ledger 记录每个候选去向
```

对应你说的"全部扫描 → AI 深入询问 → 看看"：**大体对，但要修正两点**——
1. "全部扫描"是**规则扫描 + 预算内选材**，不是全量 diff 进入 prompt；超过预算就截断（这就是 S 损失）。
2. "AI 深入询问"是 **host 执行的有界 read/search**，模型必须先在 `intent_hypotheses` 里声明 obligation 才执行；它不声明就没有补查（真实 case 里这是常态，不是 host 坏了）。
3. "看看"其实是**两段 AI + 一层机械判据**：discovery 产候选，verification 判 confirmed/dismissed/needs_context，criteria 再机械校验引文/见证，最后才发布。

## 三、每层的关键问题与下一步（含权衡）

### S：低成本补缺，别再买贵路径

- 已做：修复 Go 证据窗口、假 symbol、`follow()` 第 3+ hunk 不读、假 symbol 烧预算 → CrabTrap gold #1 从 12/26 行部分可见到 26/26；dev S 72.55%。
- 新能力：文档类 hunk 可用独立附加预算进入 prompt（`max_documentation_tokens`，默认关闭）。实测 1200 tokens 恢复 3 条 gold（S 72.55% → 75.49%），代价是 prompt +约 1.5k tokens。**建议：先关着，等 D 实验证明这部分 gold 值得付钱再开。**
- 已测不可取：把 per-file 预算按文件数摊薄（S 74→70）；unit 全量切片（实测更差）。
- 剩余大头（pika/chronicle/agents-config）是预算截断，要提升只能加 token 或开 unit，属于"花钱换 S"，需要先用 D 实验证明 D 不是瓶颈才值得。

### D：主战场

- 现状：模型在一次 discovery 里要同时做"读 diff、建假设、提 context request、产候选"，且输出预算/HTTP 预算紧；真实 case 里它经常不声明 missing evidence。
- 建议改动（按代价排序）：
  1. **强制检查项**（prompt，零调用成本）：对每个 changed 函数要求给出"调用方/错误分支/生命周期"三问答案，未答则不得直接 dismiss。风险：输出变长，可能截断。
  2. **候选二次精读**（多 1–2 次调用）：对 discovery 候选做 focused read（只带该候选 + 相关证据 + 完整函数），再判定。风险：成本 1.5–2x；对 CrabTrap 这类"helper 在远处"的 bug 最有效。
  3. **提高 discovery 输出预算 / 用更强模型只做 discovery**。风险：成本与延迟；历史 thinking 输出截断两次失败，需先解决 max_tokens/流式。
  4. **host 侧 call-graph 扩展**（不依赖模型声明）：从 changed hunk 自动解析被调用符号并读定义（成本低，但只解决"该读没读"，不解决"读了没发现"）。
- 度量：固定 3–9 dev case，先免费算 S，再跑一臂 D，报 `D/N`、`P/N`、`cost/case`；一次只改一个变量。

### P：不牺牲 precision 提 recall

- 现状：confirmed 要求 witness/引文，pending 不发 → identified 的 3/8 被扣。真实 FP 风险来自"放宽 confirmed"，不是"把 pending 展示出来"。
- 建议：**双通道**——`auto-publish` 只发 confirmed（precision 优先）；`review queue` 展示所有有证据的 pending（recall 优先），报告/Web 明确标 `needs_context`，绝不发 inline comment。pending 已经进报告，缺的是把它作为正式指标（`surfaced recall`）来度量。
- 风险：用户噪音；需要产品/UI 文案区分；不能把 surfaced 计入"已确认"统计。

## 五、关于"清理"

现在**不建议大清理**，因为漏斗刚能测，删东西会先损失定位能力。建议顺序：

1. 先跑一轮 D 实验，确认哪些路径真的没有边际收益；
2. 清理只按证据：无生产调用方 + 无测试/文档引用 + 有替代路径，三条同时满足才删，否则冻结并标注；
3. 现有明确的"冻结/历史"项（VS Code、`two_stage` legacy、`selection.py`、unit 切片默认关）保持原状，不要用删代码代替验证；
4. 真正该先清理的是工作区：82 处未提交改动 + 历史评估文档口径，先拆成独立 commit，再谈删代码。
