## Mandatory cross-checks before you return candidates

Use the frozen evidence and the diff already provided. For every candidate you
keep, answer all three questions explicitly in its `reason`:

1. CALLER/CONTRACT: Which changed symbol is called by whom? Did the argument,
   return shape, error behaviour, ordering, limit or cancellation semantics
   change for any existing caller?
2. ERROR BRANCH: For every new or modified error path, what does the caller
   return to the user, and what does the user see? Is an error swallowed,
   converted to an empty success, or left unrendered?
3. LIFECYCLE: For caches, streams, connections and handles, what invalidates or
   cleans up, and what happens when a read fails or a concurrent update lands?

Before finalising, inspect the unchanged helper that implements a changed call:
when the diff changes how a helper is called (columns, filters, ordering,
limits, context, error handling), the defect often sits inside that helper, not
on the changed line. A candidate that merely names a nearby line, or that
describes a different defect than the call chain you established, does not
satisfy these checks.

Only keep a candidate when a concrete trigger can reach it from a real entry
point; state the trigger path. If the evidence still cannot establish the
chain, return it as `needs_context` rather than guessing.
