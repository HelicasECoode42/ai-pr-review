## ADR-001 定位：本地预审优先，CI 作为影子模式，IDE 冻存

**决定**
- **主定位 A**：本地预审（push 前自检）。成功判据：开发者**愿意采纳**至少一条。
- **次定位 B**：CI 门禁，但先跑**影子模式**——只发一条可更新的 summary，不发行为内评论。
- **IDE（VS Code）冻存**：代码与已发布的 `vscode-extension/ai-pr-review-0.2.0.vsix` 保留，产品口径标为"暂不维护/暂不支持"；CI 仍编译它（防止静默腐烂），但**不作为合并门禁**。
- **Web Console 降级**为演示（Demo-first），不作为对外承诺能力。

**理由**
- 四个入口并进、没有主线：4 入口 × 2 个 prompt 家族 × 2 条链路 = 组合爆炸，每次改动都要在组合里找一致性。
- 本地是唯一能自然获得"采纳/驳回"信号的位置，而这个信号是自进化的燃料（Greptile 正是靠它学习）。
- CI 直接发评论的代价已有实测证据：CRA-only PR 合并率 **45.20% vs 68.37%**，60.2% 的关闭样本落在 0–30% 信号带。精确率没修好之前，CI 只能影子跑。
- IDE 已经交付过（.vsix 存在），删除会丢失真实工程经验；冻存成本最低。

**后果**：README 的能力表述必须同步（否则还是"宣称 4 个入口"）；IDE 的 CI 作业改名并标 `continue-on-error`。

**状态**：已采纳（用户 2026-10-15 确认"本地+CI 比较好""IDE 先取消，老版本暂时不支持也可以"）。

## ADR-002 知识层：确定性符号图 + schema 化 Markdown 条目 + 可选混合检索

**决定**：知识层分三层，**不用 GraphRAG，也不用 LLM 维护的 wiki**。

| 层 | 内容 | 生成方式 | 更新机制 |
|---|---|---|---|
| **L1 符号图** | 定义、导入边、调用方/被调用方、作用域 | **由冻结 SHA 重建，零 LLM** | 每次运行重建，**永不漂移** |
| **L2 知识条目** | 契约/不变量、项目规则、**误报目录**、判据/SOP | **人写**，Markdown + front-matter，schema 校验 | 符号不存在 → 自动 `expired`；人工确认才 `authoritative`；冲突自动降级 |
| **L3 检索** | 按 scope 过滤后 Top-K 注入 | 关键词（别名/glob/BM25）+ 可选向量 | 只做**检索**，不做抽取 |

L2 条目的必需字段：`id, scope, kind, statement, source(原文引用), version, owner, last_verified, expires_when, status`。

**理由**
- **代码的关系已经是精确的**（AST/import/调用边），用 LLM 抽图 = 把精确信息变成概率信息，还破坏可复现性——而可复现正是本项目最值钱的资产（预算账本、冻结快照）。
- GraphRAG 的维护成本**正比于仓库大小**（全库抽取、代码一变要重跑），与"本地优先、轻量"直接冲突；同一份代码两次抽取结果不同，无法进 CI 门禁。
- LLM 维护的 wiki 会**摘要漂移**，且无法机械判断"这句还有效吗"；每次更新都要重跑模型。
- 反过来，L1 可以不漂移是因为它**每次重新生成**；L2 可以不漂移是因为它**有 source 引用，能被机械校验**。
- GraphRAG 的适用场景是**非结构化文本里的隐含关系**（工单/聊天/文档）。我们目前没有这类语料；将来有了，作为 L3 的一个索引用，而不是知识来源。

**后果**：短期不需要向量库；先用 JSONL/Markdown + 关键词与 scope 过滤。L3 只在 L2 条目数超过人工可维护规模时再加。

**状态**：已采纳（用户确认知识层需要"可以更新和维护"）。

## ADR-003 核验：过滤器链 + 见证优先

**决定**：把核验从"合取式判断"改成**有名字的过滤器链**，且**机械可判定优先**：

```
provenance（已实现）→ witness（求值/执行）→ static（AST）→ re-location（行号回定位）→ dedupe → threshold
```

- `confirmed` 的最低门槛从"引文真实 + 字段齐全"提升为"**witness 或 static 见证成立，或 C 类给出可核验的契约来源**"。
- 机械结论优先于模型结论：模型只能补充解释，不能推翻求值结果。
- **每个过滤器必须记录"丢了什么、为什么"**（账本，不是静默），报告里能回答"这条为什么没发布"。

**理由**：实测证明当前判据**同时**放行可证明为假的结论（等价改写）、扣下真问题（发布 0/5）。而最强证伪手段（实际求值/跑测试）我们**完全没有**。

**状态**：已采纳；`provenance` 已实现，`witness/static/re-location/dedupe` 待做。

## ADR-004 并发：单元级并发，预算按单元切分，合并确定性

**决定**：允许并发，**以单元为粒度**。

**已实现**（`src/reviewer/unit_review.py::review_by_units`）：
- `max_workers` 参数，硬上限 `MAX_UNIT_WORKERS = 8`；`< 1` 报错，超上限**收敛**而非报错。
- **确定性输出**：结果按 plan 的单元顺序合并，**不按完成顺序**。
- **失败隔离**：单元异常记为 `failed`，不拖垮其他单元，也不拖垮线程池。
- **每单元独立预算**：单元上下文与证据预算各自独立，并发**不会**把预算偷偷合并或超支。

**理由与边界**
- 单元之间互不依赖，且受 I/O 限制（等 provider），所以用线程而非进程。
- **不能共享全局预算再并发**：那会打破"总预算"的确定性；正确做法是**静态切分**（每单元一份），派发前做成本预检。
- **不能并发**：发布（GitHub API 幂等与顺序，一个坏行号会 422 掉整批）、判定记录写入（单写者或加锁）、Critic/评测（预算与可比性）。
- **线程安全要求**：`run_unit` 必须可重入，**每个单元自己的 provider**（已写入 docstring）。
- 风险：速率限制（429）、瞬时成本放大（并发越高越快烧钱）。所以上限 8，且成本预检在派发前。

**收益（按本次实测推算）**：8 单元顺序 **627 秒** → 并发 4–6 约 **105–160 秒**；89 单元的大 PR 从约 **1.9 小时** → **20–30 分钟**。

**状态**：已实现并有测试（顺序确定性、失败隔离、上下限校验）。

## ADR-005 幂等与去重

**决定**：发布必须幂等。summary 用 HTML 标记去重（已实现）；行内评论按 **`(file, line, body)` 内容哈希**去重（借 PR-Agent 的做法）；**记住被驳回/标记 won't-fix 的条目，不再重复提**（借 PR-Agent 的 `active/resolved/dismissed`）。

**理由**：重复评论是 CRA 折损合并率的直接原因之一；"已驳回还反复提"是最快摧毁信任的行为。

**状态**：summary 去重已实现；行内去重与驳回记忆待做。

## ADR-006 版本契约：`schema_version` + `criteria_version`

**决定**：报告带 `schema_version`；运行结果带 `criteria_version`（判据版本）。**改动判据必须能解释"哪些条目因此改判"**。对外字段变更保留兼容别名（我们刚踩过 `temperature` → `temperature_requested` 的坑）。

**理由**：判据不版本化 → 改判无法归因；自进化就没有因果，只有噪声。

**状态**：已实现（`ReviewReport.schema_version` + `metrics["criteria_version"]`）。

**保留（这些是本项目真正的资产）**

- **冻结快照**（可复现性的前提）。

- **评测资产**（gold 集、ReviewBench 适配、二分图打分器）——接进 CI 即成为门禁。
- **应用边界**（`ReviewApplication` 的 provider/engine 注入，DI 已就位）。
- **入口：CLI + CI/reusable workflow**（定位 A+B 的载体）。
- **可观测产物**：usage/cache 指标、agent trace sidecar。
- 本轮修掉的真缺陷：解析失败重试、引文来源校验、静默降级收口。

**冻结 / 收敛**
- ❄️ IDE 扩展（ADR-001）。
- ❄️ Web Console → 演示。
- ❄️ legacy prompt 家族（one-shot/two-stage）→ 收敛到 grounded 一条（Phase 0）。
- ❄️ `agent` 编排壳的 8 个"假工具" → 改成声明能力与成本的真工具注册表（Phase 1）。
- ❄️ 38 篇文档 → 约 10 篇权威文档。

**状态**：已采纳。

## ADR-008 文档与工具沉淀

**决定**：只保留少量**权威文档**；判断类内容必须可校验、可版本化。

**权威文档**（目标 ~10 篇）：定位与架构 / 判据（本文 + ADR-003）/ 评测协议 / 安全 / 使用（CLI+CI）/ 路线图 / 决策记录。
**必须沉淀的工具**：`witness_eval`（求值）、`provenance_check`（已实现）、判定记录库（append-only JSONL，含 `criteria_version` 与见证）、经验库 + `recall`、`adjudicate` CLI。
**必须沉淀的清单**：**误报目录**（现有两条：等价守卫改写、无消费者的元数据键改名——两者都已实测确认）。

**理由**：没有这些，自进化就是自说自话；文档膨胀本身是"没有判断力"的症状（现 38 篇 8,134 行 > 测试 5,352 行）。

**状态**：已采纳。

## ADR-009 RSI：单主线发布工程 + playbook 增量维护（取代旧版"人写知识"）

**决定**
- **RSI 采用**：`AgentDevel 的发布工程循环`（arXiv 2601.04620）× `ACE 的 playbook 增量维护`（arXiv 2510.04618）× `DGM 的沙箱与人工监督`（ICLR 2026）。细节见 `docs/self-improving-plan.md`（该文件已按此重写）。
- **修正 ADR-002 的错误**：知识条目的**格式**用 wiki（人可读、可 diff、可评审）是对的，但我先前写成"**人写**、模型只提候选"——**这是错的**。作者应当是 **agent 自己**：ACE 证明可以**无标注监督**、用自然执行反馈学习。安全**不来自"人不让机器写"，而来自发布门禁**。
- **playbook 只准增量**：ACE 明确警告 **context collapse**（迭代整体重写会磨掉细节）；因此条目只能被追加/单条修改，**禁止整篇重写**。同时防 **brevity bias**（为简洁丢领域洞见）——条目要保细节。
- **门禁以翻转为中心**：`P2F = 0（或 ≤ 阈值）且 F2P > 0 且修复集中在声明症状` 才晋升；程序化评分优先，LLM 只补没有客观检查的部分。
- **v1 只改两类对象**：playbook 条目 + 检索策略。prompt 与代码不改（DGM 那一步需要更强沙箱，v1 不做）。
- **不用**：population/evolutionary 搜索、Self-Refine 式自评、LLM 自评当门禁。
- **held-out 只在最后用一次**；迭代期间模型/预算/工具全部冻结。

**理由**：旧方案把"安全"寄托在"人不让机器写"，代价是知识层永远长不起来；而实测显示我们最大的缺口正是知识层为空。ACE 与 AgentDevel 给出了既能让 agent 自己写、又能控制风险的机制。

**后果**：`witness_eval`（Phase 1）成为 RSI 的**前置**——没有硬信号，门禁只能靠 LLM 自评，就回到"奖励引用、不奖励检验"的老坑。

**状态**：已采纳（用户 2026-10-15 指出 wiki 才是可更新可维护的形态、RSI 应自己维护）。
