# 审查闭环设计：发现 → 取证 → 核验 → 判定

日期：2026-10-15。本文回答三件事：**这些指标到底是什么**、**别的 review agent 在核验层怎么做**、**我们的闭环该按什么判据走**。所有"别人怎么做"都注明出处，全部来自本仓库 `research/` 里已抓取的原文。

---

## 一、先把指标定义清楚（这次会话混淆过）

| 指标 | 定义 | 本次数值 | 出处 |
|---|---|---|---|
| **发现精度** | 工具提出的候选里，人工判定为真缺陷的比例 | 真实运行 **4/5 = 80%** | `docs/evaluation/identification-baseline.md` 第二节 |
| **精确率 precision** | 工具**报告出来**的条目里，有标准答案的条目比例（一对一匹配，一篇论文式） | 合成 gold 集 **2/4 = 50%** | `reports/real-run/gold-run.json` |
| **召回率 recall** | 标准答案里，被工具找到的比例 | 合成 gold 集 **2/2 = 100%** | 同上 |
| **发布召回** | 真缺陷里，最终**发布成行内评论**的比例 | 真实运行 **0/5 = 0%** | 5 条候选全被判 `needs_context` |

**"发布 0/5" 与 "精确 50%" 是不同阶段的两个数**，这次会话我把它们并列过，容易误解：

- **精确 50%** 来自合成 gold 集的**发布结果**：它发布了 4 条，其中 2 条对、2 条错。
- **发布 0/5** 来自真实仓库运行：它找到 5 条候选（我手工判定 **4 条是真缺陷**），但验证器把**全部 5 条**判成 `needs_context`（证据不足），所以**一条都没发布**。

也就是说：**内部精度不差（80%），对外产出为零（0%）**，而核验器在两个极端上都出错。

**50% 这个数要如实读**：那 4 个 case 是**故意配的 2 真 2 假**。一个"什么都报"的工具在这个集合上也会得 50%。所以 50% 的真实含义是——**它在这 4 个 case 上完全没有区分能力**（把 2 个等价改写也当成缺陷报了）。而且 n=4 不是精度估计，**真正的信号是"有一条可证明为假的结论被确认"**，不是那个百分比。

## 二、现在的核验判据是什么（代码原文）

`VERIFY_SYSTEM`（`src/reviewer/grounded_review.py`）要求模型为每个候选给出：

```
trigger → reachable call path → expected behavior → actual failure，
并解释 PR 如何引入该失败；同时尝试找反证。
confirmed 需要"足够的精确原文引用 + 具体因果解释"。
dismissed 需要"能推翻该场景的精确反证"。
上下文缺失是 needs_context，不是 dismissed。
```

代码层的合取条件（`review_grounded`）：

```python
chain = trigger ∧ expected_behavior ∧ actual_behavior ∧ introduced_by ∧ reason 都非空
      ∧ call_path 是非空字符串列表
validated  = 至少一条引文通过 _valid_citation（要求 HEAD 侧至少一条）
confirmed  ⟺  decision == "confirmed" ∧ validated ∧ chain
```

**判据的问题（本次实测）**：

1. ~~`_valid_citation` 只要求"引文落在被改动文件的行范围内"~~ → **已修**（`65d71e3`：必须出现在**已渲染给模型的证据**或**实际发送的 patch 文本**里）。
2. **`validated` 只证明"引文是真的"，不证明"结论是真的"**。`safe-index` 的引文完全真实，但它的行为主张可证明为假（德摩根等价）→ 判据**没有"结论有效性"这一项**。
3. **`chain` 只检查字段非空**，不检查这些字段是否构成有效推理。所以"字段齐全 + 引文真实"就能 confirmed。

一句话：**当前判据 = 引文真实性 + 字段完整性**；缺的是**来源合法性（已补）**和**结论有效性（未做）**。

## 三、别的 review agent 在核验层怎么做

| 工具 | 核验/降噪做法 | 对我们的启示 |
|---|---|---|
| **Claude Code**（唯一有 generate-then-verify 闭环的） | `code-review.md`：haiku 分诊 → 4 个并行代理（2× CLAUDE.md 合规、2× bug 猎手）→ **并行 validators** → filter → post。原文："If you are not certain an issue is real, do not flag it. False positives erode trust."；bug 代理被**故意不给多余上下文**（"Focus only on the diff itself"） | **独立代理问"这是真的吗"比让第一个代理"小心点"有效**；并给出 7 条误报目录（既有问题／学究式挑剔／linter 能抓的…） |
| **pr-review-toolkit**（同一仓库的兄弟插件） | "Only report issues with confidence ≥ 80"，五档锚点（`0-25` 很可能是误报或既有问题 … `91-100` 严重缺陷或明确规则违反），并按档位分组 | 数字阈值必须配**锚点说明**，否则等于没定义 |
| **PR-Agent** | **刻意不问置信度**；靠 schema 约束 + `review_filter` 类后置模块 | 置信度不是唯一出路；**结构化 schema + 后置过滤**同样可控 |
| **alibaba/open-code-review** | 独立的 `review_filter` 与 re-location 模块；分组失败降级为"一文件一组" | 核验做成**独立可替换模块**，不要塞进主 prompt |
| **Greptile** | **从团队是否采纳评论学习**（用 PR 的首末 commit 判断）+ 👍/👎 | 这是现成的自进化信号源，比"运行次数"有意义 |
| **CodeRabbit** | `reviews.profile = quiet｜chill｜assertive`，把精确/召回权衡交给用户配置 | 阈值应可配置，且**默认偏保守** |
| **Martian Bench** | 用 judge 问"these describe the same underlying issue?" 做匹配 | 判定（adjudication）本身可以是一个独立环节 |
| **Tricorder（Google）** | 产品线：**有效误报 < 10%** | 这才是该盯的目标；我们现在的 50% 离它很远 |

**关键观察**：调研覆盖的工具里，**只有 Claude Code 有"生成后验证"**；其余大多数是"发现完直接发"。所以我们的 `发现 → 取证 → 核验 → 判定` 架构**比大多数工具更完整**——你的判断是对的。坏的是**判据**，不是架构。

## 四、闭环怎么走、如何判定

### 4.1 闭环（每个 PR 一次）

```
0 冻结输入        base/head SHA + diff + inventory（已有）
1 发现 discovery  宽松取候选 C；自报置信度只作排序参考，不作判据
2 取证 retrieval  为每个候选取"能判决它"的最小证据集：定义 + 调用方 + 契约来源
3 核验 verify     对每个候选执行三类检查（见 4.2），产出 verdict + 见证 + 引文来源
4 判定 adjudicate 按 verdict × 证据强度路由（见 4.3）
5 发布 record     每条带：判据版本、来源哈希、经验 id、见证；可回滚
6 事后 learn      人工接受/驳回 + **见证离线复算** → 学习事件
```

### 4.2 三类核验检查（按"可机械化程度"排序，这是核心设计）

| 类别 | 判据 | 手段 | 能否自动定对错 |
|---|---|---|---|
| **A 机械可判定** | 两个纯表达式/纯函数在某见证输入下行为是否不同 | **实际求值** base 与 head（沙箱、无副作用表达式） | ✅ 二值、客观 |
| **B 静态可判定** | 引用/签名/调用点/解包是否一致；符号是否存在 | AST/解析器（不调模型） | ✅ 客观 |
| **C 只能模型判定** | 语义意图、契约、跨模块影响 | 模型 + **必须引用契约来源** | ❌ 需要人工或 gold |
| **P 来源校验** | 引文是否来自"已发给模型的文本" | `_provenance`（**已实现**） | ✅ 客观 |
| **R 反证优先** | 是否找到能推翻场景的反证 | 模型 + 引文（同 P 校验） | 部分 |

**规则**：A/B 任一类给出结论时，**以机械结论为准**，模型只能补充解释，不能推翻。
`confirmed` 的最低门槛从"引文真实 + 字段齐全"提升为：**A 或 B 类见证成立，或 C 类给出可核验的契约来源**。

对 `safe-index` 这种等价改写：A 类求值 → 两个守卫在所有输入上行为相同 → 没有任何见证 → **机械上无法 confirmed**。

### 4.3 判定路由（发布规则）

| verdict | 证据强度 | 去向 |
|---|---|---|
| A/B 机械见证成立 | 强 | **发布行内评论** |
| C 类 + 契约来源 | 中 | 发布，但标注"未经机械复算" |
| 引文合法但无见证 | 中弱 | 只进 summary 的"待确认"区，**不发**行内 |
| 引文非法/未展示（P 失败） | 无 | **丢弃并记事件** |
| 有有效反证（R） | 否 | 丢弃并记事件 |
| 证据不足 | — | `needs_context`，允许再取一轮（上限已有：3 轮 discovery / 2 轮 verify） |

### 4.4 怎么判定"判定得对不对"（meta 层）

两层，缺一不可：

1. **有 gold 的离线评测**：`datasets/golden/` + ReviewBench dev 划分 + 仓库自带的二分图打分器（输出 P/R/F1）。已有基线：召回 2/2、精确 2/4。
2. **机械复算（不需要人工标注）**：每条发布的结论都必须**存下见证**；离线重新求值可复算。**复算失败 = 自动判定为误报**，自动生成负样本。这让 A/B 类结论变成一个**自标注**的持续信号——这是"如何判定"最省人力的答案。
3. **人工裁决记录**（`Accepted/Rejected/Already handled/Needs context`）覆盖 C 类，进学习库。

## 五、安全问题（按可利用性排序）

| # | 风险 | 现状 | 处置 |
|---|---|---|---|
| 1 | **引文来源漏洞**：模型对**没看过的代码**编造结论，引文对上就被 confirmed | **已修**（`65d71e3`） | 保留回归测试；判定路由 P 失败即丢弃 |
| 2 | **结论有效性缺失**：真实引文 + 假结论（等价改写）被 confirmed | 未修 | 做 4.2 的 A/B 类机械复算 |
| 3 | **PR 内容注入**：被审仓库的代码/注释/PR 文本是**不可信数据** | 已有 `UNTRUSTED_INPUT_CLAUSE` | 保持；并禁止把 PR 文本当契约来源 |
| 4 | **数据外泄**：整个 diff + 证据会发往 `OPENAI_BASE_URL`（第三方） | README 有说明；`.env`/密钥邻近文件已跳过 | 允许自建 base URL；把"发到哪"写进首次运行提示 |
| 5 | **注入→外泄**：诱导模型把仓库里的密钥写进公开评论 | 有 `_secret_adjacent_reason` 跳过 | 证据路径白名单 + 输出端做密钥模式扫描 |
| 6 | **供应链**：reusable workflow 用 `uvx --from git+…@reviewer_ref` 执行**运行时的远端代码**，且带调用方 secrets | 默认 `reviewer_ref: main`（**我引入的**） | 默认改成固定 tag/SHA 并在文档里写明（见下） |
| 7 | **成本 DoS**：别人用你的 key 跑超大 PR | 有 `max_input_tokens` 上限 | 文档明确"用调用方自己的 key"；加每次 PR 的 token 上限默认值 |
| 8 | **学习库投毒**（自进化后）：写入一条"抑制某类发现"的经验 | 计划里已是"候选区 + 人工晋升" | 经验**不得覆盖 SOP**；每次注入记 id 可回滚 |

**发布权限**：自我审查 workflow 声明了 `pull-requests: write`，reusable 默认 `post_inline: false`（只发一条可更新的 summary）——保持这个默认。

## 六、自进化（Self-Improving）在这个闭环里怎么落

原来的计划（`docs/self-improving-plan.md`）把学习事件限定在"机制事实"上（请求了哪些证据、取到没有、被挤掉多少）。**现在有了更强的信号：判定结果本身**。

| 学习事件 | 来源 | 用途 |
|---|---|---|
| `witness_failed` | 离线复算发布过的见证 | **自动负样本**：收紧该类判据 |
| `citation_rejected` | P 类校验失败 | 记录"模型在哪些情况下会编造"，改进取证提示 |
| `needs_context` 聚集 | 验证阶段 | 定位"总是取不到证据"的路径/模式 → 改检索目标 |
| `human_rejected` / `human_accepted` | 人工裁决 | 覆盖 C 类判据 |
| `dismissed_with_counter` | 反证成立 | 高价值：直接可固化成"不要报"清单 |

**晋升路径**（照腾讯那篇的受控晋升）：候选经验 → 人工确认 → 规则 → SOP。护栏不变：发现模型不读 gold、经验不覆盖 SOP、每次注入可回滚。

## 七、要沉淀的文档与工具

**工具（按优先级）**

1. `witness_eval`：纯表达式/纯函数见证求值（4.2 A 类）——**最高优先，直接杀掉等价改写误报**。
2. `provenance_check`：**已实现**。
3. 判定记录库（append-only JSONL）：每条发布的判据版本、见证、来源、结局。
4. 经验库 + `recall(scope, k)`：注入 Top-K（计划 P1/P2）。
5. `adjudicate` CLI：把 gold 匹配与人工裁决变成一条命令，避免每次手写脚本。

**文档 / SOP**

1. **判据版本化**：判据以 `criteria_version` 写进报告；改判据必须能解释"哪些条目因此改判"。
2. **误报目录**（学 Claude Code 的 7 条）：把已确认的误报模式固化成"不要报"清单——本次就有两条可入册：**等价守卫改写**、**无消费者的元数据键改名**。
3. **发布契约**：哪些必须见证、哪些必须人工批准、哪些只进 summary。
4. **评测协议**：gold 集 + 机械复算 + 二分图打分的固定流程（现在写在 `docs/evaluation/identification-baseline.md`）。
5. **安全说明**：数据外泄边界、供应链固定版本要求、发布权限默认值。

**没有这些沉淀，自进化就是自说自话**：判据不版本化 → 改判无法归因；没有见证 → 无法自动判定对错；没有误报目录 → 同类误报反复出现。
