# 知识库撰写要求（可直接交给他人执行）

> 目标：把 playbook 从 **6 条** 扩到 **30–45 条**，覆盖真实缺陷分类。
> 背景数字：ReviewBench 官方 gold 共 **2623 条真缺陷 / 219 个 PR**，类别分布如下。
> 交付方式：**候选条目**（`status: candidate`），合入后由机器门禁决定是否晋升。

## 一、覆盖目标（按 gold 实际占比分配）

| 类别 | gold 条数 | 占比 | 目标条目数 |
|---|---:|---:|---:|
| correctness | 1068 | 41% | 8–10 |
| maintainability | 365 | 14% | 4–5 |
| reliability | 362 | 14% | 4–5 |
| documentation | 306 | 12% | 4–5 |
| testing | 223 | 9% | 3–4 |
| security | 98 | 4% | 2–3 |
| api-architecture | 81 | 3% | 2–3 |
| performance | 63 | 2% | 2 |
| accessibility | 57 | 2% | 1–2 |

难度参考：easy 50% / medium 41% / hard 9% —— **优先写能覆盖 easy+medium 的条目**。
范围参考：**introduced-by-pr 91%** —— 条目必须能帮助判断"**这次改动引入的**"，而非泛泛的代码质量。

## 二、条目格式（必须完全遵循，缺一不可）

```markdown
---
id: kb-XXXX
scope:
  repo: "*"                      # 或指定仓库
  languages: [python, typescript]  # 适用语言
kind: defect_pattern | retrieval_hint | contract | false_positive_pattern
statement: "一句话，可被证伪的断言"
source: "证据来源：ReviewBench case id + 文件:行（必须是真实 gold）"
intent_symptoms: [tag1, tag2]    # 与 gold 的 category 对齐
version: 1
status: candidate                # 候选，由门禁晋升
---

正文：3–6 行。说明**什么条件下该报**、**要去看哪里**（调用方？分支？错误路径？）。
```

## 三、质量红线（这些决定了精确率能不能守住 ≥0.8）

1. **必须有真实证据**：`source` 要给出 ReviewBench 的 `case_id` + 文件 + 行号，且该条在该 case 里是 **tp**。
2. **必须写反证边界**：什么情况下**看起来像但不是**缺陷（这条防假阳，是最重要的一条）。
   例：kb-0006 —— "拒绝超长正则、白名单 flag 是加固，不是回归"。
3. **不得与现有工具重复**：linter / 类型检查 / 覆盖率工具能机械判定的，**不要写**（例：未使用变量、语法、类型错误）。
4. **不得是风格/口味**：命名、排版、注释多少、函数长短（除非有具体可证的行为后果）。
5. **必须可在"单 hunk + 1 跳调用方"内判定**：需要整个仓库才能判断的条目，**不接受**（我们的上下文预算只有 6k tokens）。
6. **可被人在 1 分钟内核对**：不能是"可能需要考虑是否……"这类不可判定的表述。

## 四、批次与验收（重要：不要一次交一大批）

- **按 10 条一批**交付（例：先 correctness 10 条）。
- 每批合入后，**机器跑三项**：① 离线知识覆盖率（对 gold 的命中率）② 判据门禁 ③ held-out。
- **判据**：该批必须让**测得的知识覆盖率提升**；否则退回重写。**不许用"感觉更全了"作为验收。**
- 写条目的同时，**必须标注它属于哪个 gold category**，否则无法归因是哪一类在起作用。

## 五、当前已有条目（避免重复，供参考）

- kb-0001 假阳性模式：等价改写被误判为行为变更
- kb-0002 检索提示：去读调用方/契约
- kb-0003 契约域：count/index/total 为 int，values 为序列
- kb-0004 契约：**PR 描述承诺的机制必须真的被实现**（否则描述本身即缺陷）
- kb-0005 检索提示：并发/生命周期改动要枚举**全部入口**，不只改动的那个
- kb-0006 假阳性模式：**ReDoS 加固不是回归**

## 六、最该优先写的（按 gold 占比 × 可判定性）

1. **correctness：守卫/边界/空值/错误传播被删除或弱化**（我们已有见证机，条目让它更容易被触发）
2. **correctness：意图—实现不一致**（PR 说了 A，代码做了 B；见 kb-0004）
3. **reliability：资源生命周期、异常吞掉、重试无界、并发未串行化**（362 条）
4. **documentation：docstring/API 文档与签名不一致**（306 条，可机械判）
5. **testing：新分支/新错误路径没有对应测试**（223 条，可用覆盖率工具判）
