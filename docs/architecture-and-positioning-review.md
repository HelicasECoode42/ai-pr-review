# 架构与定位评审（2026-10-15）

本文是对整个项目的回顾：**现状盘点 → 为什么效果这么差 → 与别的 harness / 腾讯四层架构对比 → 定位审视 → 痛点 → 分阶段路线图**。数据都来自本仓库实测。

---

## 0. 一页诊断

**当前 harness 是一个"单遍提示流水线"，但它穿着"agent"的外衣。** 三句话：

1. **模型不能动手。** 注册的 8 个"工具"（`fetch_pull_request`、`fetch_changed_files`、`scan_risks`、`analyze_cross_file`、`build_rule_only_report`、`one_shot_ai_review`、`render_markdown`、`render_json`）是**固定的流水线阶段**，不是模型可选择的动作；`policy.py` 按 diff 规模**确定性地**选一个阶段。模型唯一的选择权是 grounded 路径里的 `context_requests`（只有 `read`/`search`，最多 3 轮，**不能执行任何东西**）。
2. **输入被人为截断。** 真实 187 文件 PR：默认预算下只有 **22/193 个 hunk（11%）** 进入 prompt；要放下整份 diff 需要 **588,648 tokens**，而模型窗口是 12.8 万。所以模型被喂了一个残缺的仓库视图。
3. **判据奖励"引用"而不奖励"检验"。** confirmed 的条件是"字段齐全 + 引文真实"。于是它**同时**：把真问题扣成 `needs_context`（真实运行 **发布 0/5**），又把可证明为假的等价改写确认下来（合成集**有一条明确误报**），甚至能对**从未展示过的代码**背书（`mod_23`，已修来源校验）。

**一句话结论**：一个"裸的"编码代理（有 shell、能跑测试、能自己找文件）**比现状更强**，因为我们的 harness 抽掉了它的最强武器——**动手证伪**，同时给了它残缺的输入和一个错误的判据。**所以是的，问题在 harness，而且不是 bug 层面，是形状层面。**

## 2. 为什么效果这么差（按贡献度排序）

| # | 原因 | 证据 |
|---|---|---|
| 1 | **不给模型动手能力** | 核验只能靠"读+推理"。最强的证伪手段（**把两个表达式实际求值、跑一下测试**）完全缺失。`safe-index` 那条等价改写，只要执行一次就能否掉，而我们只能让模型"再想想" |
| 2 | **输入残缺且不对称** | 187 文件 PR 默认只送 11% 的 hunk；模型对没见过的东西只能猜（`mod_23` 就是猜对了——但那不是能力，是运气） |
| 3 | **判据方向反了** | 门槛设在"证明成立"（难），而非"找反证"（易）。结果是**真问题全被扣**（0/5 发布），**假结论反而通过** |
| 4 | **"agent"是空壳** | 8 个"工具"是流水线阶段，模型无法编排；`policy.py` 是确定性选择器。这里没有 ReAct 循环，只有一条带 JSON schema 的流水线 |
| 5 | **知识层几乎为零** | 没有契约库、没有不变量库、没有项目规则、没有"历史误报目录"、没有"哪些评论被驳回"的记忆。每次审查都从零开始 |
| 6 | **没有采纳回路** | 不知道作者有没有处理某条评论 → 无法知道好坏 → 无法学习（Greptile 正是靠"首末 commit"学这个） |
| 7 | **变体爆炸** | 两个 prompt 家族（legacy one-shot/two-stage + grounded discovery/verify）× 两条链路（普通 / agent）× 四个入口；每次改动都要在组合里找一致性 |
| 8 | **文档在代替产品** | docs 8,134 行 > tests 5,352 行；37 篇文档、0 个发布。**文档成了主要产出物**，这不是自进化，是自我安慰 |

## 3. 别的 harness 长什么样（引用自 `research/` 已抓原文）

| 工具 | harness 形状 | 对我们的启示 |
|---|---|---|
| **Claude Code** | haiku 分诊 → 4 个并行代理（2 规范合规、2 bug 猎手）→ **并行 validators** → filter → post。bug 代理**故意不给多余上下文** | ① **生成与验证是两组独立代理**；② 显式"高信号"门槛 + 7 条误报目录；③ 代理有真工具（自己能读、能搜、能跑） |
| **alibaba/open-code-review** | 元数据分组 LLM → 每组 1 次 Plan + ≤2 轮 Main → **`review_filter`** + **re-location** 模块；并发 8；超额组标 `failed(budget)` | **核验必须是独立可替换模块**；预算超限要显式标记，而不是静默丢弃。**这是我们最该抄的形状** |
| **PR-Agent** | 无 agent 循环；确定性编排 + 严格 schema；**刻意不问置信度**；跨运行行内去重（内容哈希） | 结构化 schema + 后置过滤**本身**就够用；重复评论要按内容哈希去重 |
| **CodeRabbit** | 把机械检查**外包给真工具**（semgrep/ast-grep/eslint/ruff 50+），模型只做语义 | 别让模型干机器能干的事 |
| **Greptile** | 从"团队是否采纳评论"（PR 首末 commit）+ 👍/👎 学习 | 现成的自进化信号源 |
| **reviewdog** | `-filter-mode: added`；超出 diff 的评论降级为 Check 注解 | 发布位置必须回落到合法区间（我们已做锚定校验） |
| **Martian** | judge 问"these describe the same underlying issue?" | 判定（adjudication）可以独立成环节 |

**共同点**：能打的 harness 都**把"验证"当成独立模块**，并**给代理真工具**。我们两样都缺。

## 4. 与腾讯四层架构对照（来自用户提供的那篇文章）

| 腾讯的层 | 它的内容 | 我们的现状 | 缺口 |
|---|---|---|---|
| **数据层** | 多模态数据接入、清洗、索引、变更记录 | 冻结快照 + diff + 语法索引 | ❌ 没有历史/变更记录/工单等旁路数据 |
| **知识层** | 知识库、**SOP**、代码资产、拓扑 | **几乎为零** | ❌❌ **最大的缺口**：没有契约库/不变量/规则/经验 |
| **Agent 层** | 编排、工具、**证据链**、变更影响分析 | 流水线 + 只读工具 + 证据包（有预算账本） | ❌ 无执行工具、无真循环、影响分析只有名字匹配的弱关系 |
| **应用层** | 人机协同、报告、验证、可追溯 | 4 个入口 + 报告 | ❌ 无采纳回路、无判定记录 |
| **横切：Trace** | 全链路可追溯 | agent trace sidecar（部分） | ⚠️ 无判据版本、无判定记录 |
| **横切：评测** | 持续评测 | 有 gold/打分器，**不进 CI** | ⚠️ 有工具没用起来 |
| **横切：自进化** | 经验受控晋升 | 只有计划文档 | ❌ 未实现 |

**关键对照结论**：腾讯那套的重心在**知识层 + 证据链 + 受控晋升**；我们**把力气全花在数据层和 Agent 层的提示工程上**，知识层是空的。这也解释了为什么单次表现上不去——**没有可复用的领域知识，每次都在重新推理**。

## 5. 定位审视（最该先回答的问题）

现状是四个入口、两套 prompt、两条链路，**没有一条"用户拿它做什么"的主线**。必须选一个：

| 候选定位 | 用户 | 成功的判据 | harness 形状 |
|---|---|---|---|
| **A. 本地预审工具**（push 前自检） | 单个开发者 | 我本地跑它、**愿意采纳**至少一条 | 单进程、可选执行测试、低延迟、便宜 |
| **B. CI 门禁**（团队） | 团队 | 精确率够高，**不拖慢合并**（CRA-only PR 合并率 45% vs 68% 的教训） | 幂等发布、去重、预算上限、影子模式 |
| **C. IDE 内联** | 开发者 | 建议能落到光标处、可直接改 | LSP 形态、增量 |

**A 是最容易做对、最能积累数据的定位**：本地可执行测试（证伪能力最强）、成本可控、失败只影响自己、能自然收集"采纳/驳回"。B 需要先解决精确率与误报成本，否则就是制造合并摩擦。C 需要另外的工程量。

**我的建议：锁定 A，把 B 作为 A 的只读影子模式（只发 summary、不发评论），C 暂缓并明确标注实验。**

## 6. 痛点清单（带证据，按"影响 × 可修性"排序）

1. **核验判据无效**（可证明为假的结论通过；真问题被扣）→ 修法明确、可机械判定。
2. **没有执行能力** → 一个沙箱执行器就能同时修 1 的一半。
3. **知识层为空** → 契约/不变量/项目规则的沉淀与按需注入。
4. **输入残缺** → 分片+按需取证（但**必须在核验修好之后**，否则分片只是放大错误）。
5. **无采纳回路** → 采集评论后续处置。
6. **评测不进 CI** → 已有 gold/打分器，接进 CI 几乎免费。
7. **变体爆炸** → 砍掉 legacy prompt 家族，单一主路径。
8. **文档膨胀** → 37 篇裁到 ~10 篇权威文档。

## 7. 可以干什么：分阶段路线图

每阶段标注**成本 / 依赖 / 验收**。

### Phase 0 — 止损与收口（0 元，离线可验证）
- 砍掉 legacy prompt 家族，**单一主路径**；入口只做 I/O 适配。
- 报告加 `schema_version` + `criteria_version`；对外字段变更必须留兼容别名（我们刚踩过 `temperature` 改名的坑）。
- `docs/` 从 37 篇裁到 ~10 篇：定位 / 架构 / 判据 / 评测 / 安全 / 使用 / 路线图。
- 打第一个 tag（0.1.0），把 Web/IDE 标成 experimental。
- **验收**：`pytest` 只跑一条链路；CI 绿；`docs` 行数 < `tests` 行数。

### Phase 1 — 给 harness 装上"手"（低 token 成本，**最高杠杆**）
- **`witness_eval`**：对纯表达式/纯函数类结论，**实际求值** base vs head（沙箱、白名单、无网络、超时）。
- **`run_tests`**：允许在受控沙箱里跑**指定**测试文件（只读挂载 + 超时 + 无网络），作为反证的来源。
- 把两者作为**新的证据类型**接进 `EvidenceBundle`，并在 VERIFY_SYSTEM 里要求"能执行就执行"。
- **验收**：合成 gold 集上 `safe-index` 这类等价改写**机械上无法 confirmed**；精确率从 2/4 提升且可复算。

### Phase 2 — 核验过滤器链 + 判定记录（0 元）
- 把核验拆成**有名字的过滤器链**（借 alibaba 的 `review_filter`/re-location 与 Java 的 pipeline 思路）：
  `provenance（已做）→ witness（Phase 1）→ static（AST）→ re-location（行号回定位）→ dedupe（内容哈希）→ threshold`
- **每个过滤器必须记录"丢了什么、为什么"**（账本，不是静默）；报告里能看到一条候选的完整去向。
- 判定记录 append-only：`criteria_version` + 见证 + 结局，可回滚。
- **验收**：任取一条候选，能回答"它为什么没发布"；关闭任一过滤器可复现差异。

### Phase 3 — 知识层（腾讯架构里我们缺的那层）
- 三类可检索知识：**契约/不变量**（函数级前置后置）、**项目规则**（从 `AGENTS.md`/`CLAUDE.md`/历史评论提取）、**误报目录**（本次已有两条：等价守卫改写、无消费者的元数据键改名）。
- 按 scope 检索 Top-K 注入，**经验不得覆盖 SOP**；候选区 → 人工确认 → 规则 → SOP（受控晋升）。
- **验收**：注入 Top-K 后，`needs_context` 数量下降且不增加误报（有 A/B 协议）。

### Phase 4 — 分片 + 迭代（**依赖 Phase 1/2**）
- 按 `ReviewUnit` 逐单元审查 + 按需取证；预算与失败逐单元记账。
- 只在核验修好后开启：否则 46 次调用换来 2 条误报（已实测）。
- **验收**：大 PR 的单元覆盖率与精确率同时不低于单次路径。

### Phase 5 — 采纳回路 + CI 门禁
- 采集"评论后的 commit 是否处理了它"（Greptile 思路）+ 👍/👎 → 进学习事件。
- gold 集 + 机械复算进 CI（离线、0 元）：**回归门禁**。
- **验收**：质量回退能让 CI 变红。

## 8. Java 后端思路对照（不用 Java）

| 模式 | 我们缺什么 | 具体动作 |
|---|---|---|
| **分层 + 依赖倒置** | 基本有了（`application/protocol.py` 是端口层） | 明确 `domain 不依赖 transport`；provider/git 全部走注入 |
| **契约优先 / DTO 版本化** | 缺 `schema_version`；刚破坏过一次字段兼容 | 报告加版本 + 兼容别名 + 弃用策略 |
| **管道/过滤器链** | 核验是一坨合取式，无法单独开关/归因 | Phase 2 的过滤器链 |
| **幂等 + 去重** | 每轮重发评论（只有一条 summary 做了去重标记） | 内容哈希去重 + 驳回记忆 |
| **可观测性（Trace/Metrics）** | 有 token 账本、缺**判定账本**和判据版本 | Phase 2 的记录库 |
| **弹性（超时/重试/隔离/熔断）** | 有超时和 1 次解析重试；无按单元的隔离与熔断 | bulkhead per unit；402/429 熔断；预算上限 |
| **配置外置 + 灰度** | 缺影子模式与开关治理 | summary-only 影子模式；按 repo/规模灰度 |
| **测试金字塔 + 回归门禁** | 有单测；缺契约测试门禁 | gold 契约测试进 CI |
| **迁移与兼容** | 无版本化判据 | `criteria_version` + 评测基线 |
| **SPI / 可插拔** | 工具注册表存在但只读、且非模型驱动 | 工具声明**能力与成本**（read/search/exec），exec 走 SPI 沙箱 |

## 9. 技术栈评价

- **保留**：pydantic（契约）、httpx、typer、structlog、tiktoken、tree-sitter、pytest、ruff。这些够用且轻。
- **补齐**：一个**受控执行器**（进程级沙箱：超时 + 只读挂载 + 无网络 + 白名单）——这是 Phase 1 的载体。
- **不要引入**：向量数据库（先用 JSONL + 关键词/scope 过滤）、消息队列、K8s、Java 生态。
- **可选**：SQLite 作为判定/经验库（当 JSONL 超过几万条再换）。

## 10. 如果只做一件事

**给 harness 装上执行能力，并把核验改成过滤器链。**

理由：它同时修掉"精确率"、"真问题被扣"、"来源与有效性"三件事，且**离线可验收**（合成 gold 集已有基线：精确 2/4），成本低于任何分片方案。**分片、知识层、自进化都应该排在它之后**——在一个不能证伪、判据又不能归因的 harness 上做它们，只会把错误放大。
